## Summary

A finished, well-styled seasonal static site that works, but it has a real consent/privacy defect: index.html ships CSS for a consent checkbox and a scrollable privacy notice, yet neither is present in the page markup — the webhook nonetheless records `consented: 'Yes'` for every visitor while silently collecting IP, geolocation, device, browser, language, referrer, and full user-agent. The Apps Script endpoint is world-writable with no auth, rate limiting, or validation, and 4.1 MB of binary assets (one of them dead/unreferenced) is committed to git with no .gitignore. Code quality is otherwise clean (no leftover console spam, good RTL/meta hygiene), but maintainability suffers from triplicated inline CSS theme variables. Overall grade: C

## Critical

### [C1] Visitor tracking without the consent UI it claims, and silent PII collection
- Where: index.html:519-580 (collection + `consented: 'Yes'`), index.html:213-290 (orphaned consent/privacy CSS), index.html:435-477 (body markup)
- Evidence: `fetchVisitorInfo()` calls ipapi.co on page load and POSTs `{ip, city, region, country, device, browser, screenSize, language, referrer, consented: 'Yes', userAgent}` to the webhook on Enter; the body contains only the crescent, title, subtitle, divider, and Enter button — there is no `.consent-check` checkbox and no `.privacy-text` element rendered, even though both are fully styled. The eid-mubarak.html footer (line 2222) links "سياسة الخصوصية" (Privacy Policy) to index.html, which displays no privacy text at all.
- Impact: The site collects and stores personally identifiable data (IP + geolocation + full UA) for every visitor without showing any disclosure or obtaining real consent, while hardcoding `consented: 'Yes'`. This is a privacy/compliance exposure and contradicts the page's own design intent and the "Privacy Policy" link.
- Fix: Either (a) restore the consent checkbox + privacy-notice markup that the CSS already supports, gate the Enter button on it, and set `consented` from the actual checkbox state; or (b) if tracking is intentional and minimal, add a visible disclosure and remove the misleading hardcoded `'Yes'`. At minimum, render an actual privacy notice so the footer link resolves to real content.

## High

### [H1] World-writable backend endpoint with no auth, validation, or abuse protection
- Where: google-apps-script.js:42-80 (doPost/doGet), index.html:566 (hardcoded WEBHOOK_URL), setup notes ("Who has access: Anyone")
- Evidence: `doPost` JSON.parses `e.postData.contents` and `appendRow`s every field with no shared secret, origin check, honeypot, size cap, or rate limit; the deployment instructions explicitly set access to "Anyone"; the `/exec` URL is published in client-side index.html.
- Impact: Anyone who finds the URL (it is in shipped HTML) can flood the "Eid Visitors Log" sheet with arbitrary rows, inflating quota usage and poisoning the data. There is no integrity guarantee on any logged value.
- Fix: Add a shared-secret token check at the top of `doPost` (reject if absent/mismatch), validate/cap field lengths before appendRow, and consider a hidden honeypot field. Note that a token in client JS only deters casual abuse; for real protection move logging behind a server you control or accept the sheet is public-write.

## Medium

### [M1] 4 MB+ of binary assets committed to git, including a dead unreferenced file
- Where: git-tracked files: eid-song.m4a (4,013,540 bytes), photo_2026-03-20_00-37-11.jpg (152,947 bytes)
- Evidence: `git ls-files` shows both binaries tracked. `grep` across all HTML/JS confirms photo_2026-03-20_00-37-11.jpg is referenced by no page (dead asset); eid-song.m4a is referenced only at eid-mubarak.html:1786.
- Impact: Repo bloat (every clone pulls 4.1 MB of binaries that never diff well); the JPG is pure dead weight shipped to no purpose.
- Fix: Remove photo_2026-03-20_00-37-11.jpg from the repo (it is unused). For eid-song.m4a, move to external/CDN hosting or Git LFS and reference by URL; if it must stay, accept the bloat but at least document it.

### [M2] No .gitignore in the repo
- Where: repo root (no .gitignore present)
- Evidence: `ls -la` shows no .gitignore; `.claude/` currently shows as untracked in `git status`.
- Impact: Easy to accidentally commit local editor cruft, OS files, or the .claude/ tooling directory.
- Fix: Add a .gitignore covering at least `.claude/`, `.DS_Store`, `Thumbs.db`, and editor temp files.

### [M3] CDN scripts loaded without Subresource Integrity (SRI)
- Where: qrcard.html:10-11 (qr-code-styling@1.5.0 from unpkg, html-to-image 1.11.11 from cdnjs)
- Evidence: Both `<script src="...">` tags lack `integrity` and `crossorigin` attributes.
- Impact: If either CDN or a pinned-version artifact is tampered with, malicious JS runs in the page with no detection — and qrcard.html builds an image the user downloads.
- Fix: Add `integrity="sha384-..."` and `crossorigin="anonymous"` to both script tags (hashes available from the CDN/jsdelivr SRI tooling), or self-host the two libraries.

### [M4] Triplicated inline CSS theme variables / no shared stylesheet
- Where: index.html:24-31, qrcard.html:13-19, eid-mubarak.html:24-30 (each redefines `--purple-deep`, `--purple`, `--gold`, `--gold-light`, `--gold-deep`, etc.)
- Evidence: The same `:root` palette is copy-pasted into all three pages' inline `<style>` blocks.
- Impact: Any palette change must be made in three places; drift is likely (eid-mubarak.html already adds pink vars the others lack).
- Fix: Extract shared theme tokens into a single `theme.css` linked by all three pages; keep page-specific rules inline if desired.

## Low

### [L1] Geolocation fetch fires before any user interaction
- Where: index.html:541 (`fetchVisitorInfo()` called immediately on load)
- Evidence: The ipapi.co request runs at page load, well before the Enter click, so the network request to a third party happens for every visitor regardless of whether they proceed.
- Impact: Third-party request and data exposure occur even for visitors who bounce. Minor, but reinforces C1.
- Fix: Defer the fetch until the user has consented/clicked Enter.

### [L2] `mode: 'no-cors'` webhook POST silently swallows all errors
- Where: index.html:568-579
- Evidence: The fetch uses `mode: 'no-cors'` and an opaque response; `.finally()` redirects regardless, so a failed/blocked log is indistinguishable from success.
- Impact: Logging failures are invisible; no retry or signal. Acceptable for a fire-and-forget log, but worth noting.
- Fix: If reliability matters, switch the Apps Script to return proper CORS headers and inspect the response; otherwise document that logging is best-effort.

### [L3] `console.error` left in production download path
- Where: qrcard.html:258
- Evidence: `console.error("Failed to generate image", err);` inside `downloadCard()` catch block.
- Impact: Negligible; it backs a user-facing alert, so it is reasonable error handling rather than stray debug output.
- Fix: Optional — leave as-is, or gate behind a debug flag.

## Optimizations

- Self-host or lazy-load the two CDN libraries in qrcard.html so the QR page does not depend on two external origins (also enables SRI per M3).
- Externalize all three pages' shared CSS into one cached stylesheet (M4) to cut duplicated bytes and ease theming.
- eid-mubarak.html is 89 KB of fully-inlined CSS/JS; if load time matters, split critical CSS from the animation JS so the card paints before the heavier scripts parse.
- Move eid-song.m4a (4 MB) off the git repo and behind a CDN/`preload="none"` so the audio is fetched only when the user opts to play it.
